# 台彩免費同步方向與先前 API 串接準備

最新狀態（2026-10-28）：使用者確認**免費取得資料是必要條件**，不採用需付費的 JBot API，改找其他免費方案。先前 API 草稿保留供參考，不推進付費申請、試用轉付費或訂閱。後續已依使用者授權實作免費 Chrome 同步，見[實作／安裝指南](browser-sync-guide.md)；本文件保留方案評估時間點，後續正式啟用紀錄以同步指南為準。

## 目前免費候選與查證範圍

查閱台彩公開說明、政府資料開放平臺及 Chrome 官方能力文件，尚未找到可確認長期免費、允許本用途、且提供台彩最新 NBA 賽前盤的公開 API。這是本次搜尋結果，不是宣稱全網不存在。政府平臺搜尋到的[公益彩券開獎資料](https://data.gov.tw/dataset/72921)屬樂透等開獎號碼，不符合 NBA 台彩盤口需求。既有國際 Odds API 也不能代替台彩。

| 候選 | 額外資料訂閱費 | 與原需求的符合程度 | 限制／狀態 |
|---|---|---|---|
| 自製 Chrome 盤口同步擴充套件 | 無第三方資料 API 訂閱費 | 最接近：一般 Chrome 正常開啟台彩 → 決策中心要求同步 → 傳送必要盤口至 Python，省掉 HAR 匯出 | 技術候選，尚未在台彩實測；需安裝及明確授權指定網域，不能保證手機相同支援 |
| 本機 HAR 自動接收／匯入 | 無第三方資料 API 訂閱費 | 可省指令與檔案搬移 | 仍需手動匯出 HAR，不完全滿足使用者的免 HAR 目標，只作備援候選 |
| 手動填入／貼上盤口 | 無第三方資料 API 訂閱費 | 小量比賽可用，沒有 HAR | 不會自動取得最新全聯盟盤口；需處理主客、盤線、賠率、時間與完整性驗證，不能當一鍵同步 |
| 長期免費台彩資料 API | 未找到可確認者 | 若存在且授權／內容完整會最直接 | JBot 共用試用有額度與排程限制，不能當長期免費解法 |

上述「免費」指沒有新增資料訂閱費，不表示現有 Cloudflare／Railway／Supabase 的用量完全沒有成本。

### Chrome 候選的可行性與邊界

Chrome 官方提供[指定 frame 的腳本能力](https://developer.chrome.com/docs/extensions/reference/api/scripting)、[網頁至擴充套件通訊](https://developer.chrome.com/docs/extensions/develop/concepts/messaging#external-webpage)，以及[本機載入未封裝擴充套件](https://developer.chrome.com/docs/extensions/get-started/tutorial/hello-world#load-unpacked)。這些證明瀏覽器具備組成此流程的能力，**不代表台彩已實測成功或已同意此用途**。

預定先驗證：一般桌面 Chrome 正常載入 sportsbook／NBA 內容後，僅在使用者要求時取得必要盤口，標示每筆真實回應完成時間；不讀取或上傳 cookie、Authorization、登入、帳戶或下注資料。只允許明確指定的台彩及自家平台網域，不申請全網站權限、不移除 CSP／CORS／其他保護，不使用 stealth、proxy 或 CAPTCHA 解題。遇到 challenge、403 或 429 就停止並回報；不能以安裝擴充套件為由繞過網站防護。

台彩盤口位於與外層網站不同網域的 iframe（現有 `core/odds/twsport.py` 已記錄），所以不能只在決策中心加一般跨網域 fetch 就宣稱完成。需確認 frame 與權限、正常載入的資料結構及全場／上半場覆蓋；正規化、定價、風控仍沿用 Python。

新查到的[台彩運動資訊來源及版權聲明](https://article.sportslottery.com.tw/zh-tw/declaration/96)說明運動資訊經 Sportradar 授權，未經同意禁止轉載。不能從免費瀏覽推定可公開展示或自由再利用；應確認個人處理／儲存範圍，並避免把取得資料直接寫進目前公開的盤口 API。這是權利待釐清的範圍，不把「能讀到」當作法律授權。

此處為選案時的評估；後續本機實作與驗證進度見[同步指南](browser-sync-guide.md)。尚未安裝助手或連線台彩實測，也未改用新的正式資料來源。

## 啟用前必須拿到的答覆與樣本

- 用途許可：包含個人投注輔助、三個雲端平台的處理／儲存、保留期限及可展示的原始／衍生欄位。
- 試用與付費專屬憑證範圍、呼叫頻率、額度與方案；在確認前不呼叫帶「使用即接受條款」的 API，也不使用共用 key 排程。
- 今天與明日已開盤、賽前／賽後、變更時間、封盤／停售、單場／串關資格、各支援玩法及錯誤的脫敏樣本。無法提供的玩法維持 unavailable／unsupported。
- 時區與時間定義、整數盤及 OT 結算、完整清單與增量語意，足以判定 quote freshness；不能用猜測補欄位。

如果供應商只供歷史盤口，或無法辨識仍開放的單場盤，則不能支援目前決策中心的一鍵更新用途。可以另作歷史研究評估，但須重新確認範圍，不能假裝已滿足本需求。

## 預定的一鍵資料流程

```mermaid
flowchart LR
    A[登入後按更新台彩盤口] --> B[Hono 驗證與建立冪等工作]
    B --> C[Supabase 工作佇列]
    C --> D[Railway Python 領取工作]
    D --> E[已獲授權的供應商 API]
    E --> F[Python 驗證 正規化 對戰比對]
    F --> G[盤口快照與來源稽核]
    G --> H[既有定價 注碼 決策物化]
    H --> I[頁面取得結果與最新有效額度]
```

這是預定設計。沿用現在 Cloudflare Pages／Railway／Supabase 架構；Hono 不執行 Python 或重算 EV／Kelly，也不取得供應商 key。網站將工作入列，Python 背景執行；前端顯示實際進度，不能把 HTTP 202「已受理」當匯入完成。

排程器需有獨立、便宜的待辦檢查；無工作時不呼叫供應商。具體輪詢頻率與每日背景抓取是否開啟，在確認授權、額度和執行成本後決定。本機 D1 僅供頁面與 API 驗收，不假裝已接上 Railway worker。

### 網站互動契約

- 尚未取得授權、憑證未設定、worker 心跳過期或 migration 未套用：明確顯示尚未啟用／目前不可同步，不顯示已更新。
- 具備必要條件後，在決策中心提供「更新台彩盤口」，保留所選 betting day。日期轉為供應商查詢日應依確認後的契約，不能假定與台灣日期相同。
- 重複點擊／重送共用 `client_request_id`；全站只有一個進行中的供應商抓取，其他人／分頁共用結果，並有伺服器冷卻與額度保護。
- 工作狀態為排隊、匯入中、匯入完成、部分完成、失敗、逾時／結果待確認；網路不明或行程中斷不能盲目重試、扣額度或宣稱成功。
- 收據顯示供應商、實際取得時間、供應商資料時間、成功比對場數／市場數及未支援玩法；有無有效可操作額度仍由當前 Python 物化結果決定。
- 若匯入成功但定價／物化失敗，分別顯示，不沿用舊額度冒充更新成功。舊資料與原始時間保留，失敗不自動延長有效期。

### 憑證、存取與部署

- 專屬 key 只存 Railway secret；如需本機測試，存於被忽略的 `pipeline/.env`。實際變數名稱於實作時定義，不把尚未實作的名稱寫成現有設定。
- 不透過前端輸入／儲存 key，不寫進 HTML、瀏覽器 storage、Cloudflare bundle、工作內容或日誌。
- 現有 `/api/games*`、`/api/odds/:gameId`、賽事頁面是公開讀取。**私人用途授權並不足以直接把 API 盤口寫入現行公開介面**：實作須先對授權來源資料加登入／擁有者限制，或取得明確公開展示許可；定價、盤口歷史、快取與衍生欄位也須按條款處理。
- 更新端點需驗證 session、來源、請求內容、可查日期及使用者權限；不能沿用公開 API 即認定可讓任何人消耗付費額度。
- 需要新增佇列／來源稽核 schema 時，同時維護 Postgres 與 D1 migration；新 Postgres 表維持 RLS、API 角色撤權與後端存取契約。正式 migration、secret 與部署另行確認。

## Python adapter 的資料契約

| 欄位／情境 | 準備採用的處理原則 |
|---|---|
| 供應商 vs bookmaker | 台彩是市場／bookmaker，JBot 是資料提供者；保存獨立 provider、事件 ID、parser 版本與授權來源，不冒充官方直接擷取 |
| time / date | 依供應商確認的時區與日期規則轉 UTC，再對應既有 NBA games；不靠台彩場次編號單獨認定全球唯一 |
| odds[].update | 保留供應商原值及解讀後 UTC；價格變更時間不等於最後確認時間，必須分開保存 |
| fetched_at / available_at | 記錄實際回應完成及首次可得時間；供應商歷史 update 不代表本專案當時已取得資料，不回填歷史 paper |
| last_seen / freshness | 在供應商確認「此報價仍開放且已更新查核」的契約成立前，不把每次 API 呼叫時間當新的盤口確認時間 |
| normal | 在確認為全場兩向且含 OT、有效及可單場後，才映射既有 ml；規則不明不產生可操作資格 |
| handi | 先確認主隊顯示線、主客 side、OT、push、主盤與多線語意，再映射 spread；不任選一條較有利線 |
| total | 完整 over／under 同一次回應配對，確認 OT／push；不拼接不同時間或來源 |
| s | 契約須定義單場與最少串關數；未知／需串關不當作既有單場策略的可操作盤，不能暗改 execution-v1 |
| m | 確認是否為主盤與缺值語意；不把範例 `false` 猜成停售，也不自行挑選最有利盤 |
| h1 | 公開文件未證實支援；無樣本與結算規則就保持 unavailable，不用全場盤推導上半場 |
| 缺邊、缺市場、空 data | 區分合法空集合、部分回應、封盤與 parser 錯誤；無法辨識時失敗關閉，不假裝無比賽或維持已停售報價 |
| 回應 user 欄位 | API 範例包含訂閱 email、expiry 及額度；只取經驗證的額度整數，排除身分／憑證，不原樣輸出或存 raw 樣本 |

下游沿用 `core/odds/canonical.py`、matching／store，再進 `pricing`、`sizing` 與 `decision`。現行 `run_odds_job` 的 parser、每批觀測時間、series 及去重目前假定 twsport／oddsapi 來源；串接時需明確擴充 provider 與逐筆時間，不可只更換 URL 後偽裝成既有 HAR parser。

來源權利、單場資格或時間仍無法驗證的市場，不得進入 actionable；維持 `ml-v2.0`、`dist-v2`、`risk-v1`、`execution-v1`。缺少台彩資料時不以國際盤替代。

## 後續實作與驗收順序

1. 取得用途／儲存／展示許可、價格、專屬 key 與脫敏樣本；先確認這個 API 確實適合賽前單場決策。
2. 以樣本離線實作 adapter／契約檢查與回歸；拒絕壞時間、未來資料、缺邊、串關盤、不明封盤、未知結算與過期報價。
3. 實作工作佇列、原子 claim、全站限流／額度、冪等性、worker 與頁面按鈕；憑證不離開 Python。先完成授權來源讀取限制。
4. 在獨立 D1／隨機 Postgres schema 驗證權限、重送、併發、失敗、重啟、逾時及「已匯入但尚未物化」等流程。不得 seed 正式 DB。
5. 經使用者確認授權／費用／條款後，才做獲准的真實 API 唯讀試接與樣本比對；一次明確請求，不無限重試。正式匯入、migration、部署另依授權範圍操作。
6. 以真實賽前資料確認：按鈕 → API → Python → 快照 → 定價／注碼 → 決策中心，顯示資料提供者與原始時間。未測到上半場／封盤／結算的部分明確保留未驗證。
