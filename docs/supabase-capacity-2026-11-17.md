# Supabase 容量歸檔與驗證（2026-11-17）

正式 NBA Postgres 的唯讀量測是 787,639,443 bytes（約 788 MB）。大表主要是有效歷史資料和索引。一般 VACUUM 只能讓 PostgreSQL 重用空間，容量要在資料移出原表並整理資料檔後才會下降。[Supabase 容量說明](https://supabase.com/docs/guides/platform/database-size)

初步估計，整理後可回收約 367 MB 淨空間，NBA 約 421 MB，加 LifeOps 約 455 MB。方法是用原表實際大小及候選比例估算可回收部分，再加上本機 PostgreSQL 17 對正式資料樣本量得的壓縮開銷。壓縮樣本數分別為 28,809 筆傷病、9,203 筆決策或明細及 2,307 筆注碼。資料分布、Postgres 索引密度與月底平均均會影響結果，實際值以維護後 `pg_database_size` 和官方 Usage 為準。免費方案可以先走這個方案，以 500 MB 為上限並觀察後續成長。

已在本機隔離 Postgres 通過 32 項 DB 回歸與 712 項離線測試。測試包含原欄位及 ID 完整往返、cutoff 前後的傷病查詢／快取一致性、實際下注與每日日終決策保留、注碼保留、歸檔範圍改變時原子失敗、原有不可變觸發器仍有效。正式環境目前只有唯讀量測。

## 等待核准的正式步驟

1. 先確認 Supabase 磁碟餘量、連線與 WAL 空間，以及可以短暫維護的時段。匯出一致性備份到私有的本機位置，驗證還原後才移動正式資料。
2. 僅執行 `0015_quota_archive.sql`，確認三張新表啟用 RLS 且公開 API 角色沒有權限。部署 NBA 傷病載入器並驗證能同時讀取原表與歸檔表。
3. 使用新的唯讀 preview 核對同一 cutoff 的列數。專用維護交易會重新挑選並比對確認過的列數。壓縮副本及原表移除原子提交。只有已被取代的決策原表需要在鎖表的維護交易內暫停兩個不可變觸發器，交易結束前即還原。實際下注、帳本與稽核事件保留在原表。
4. 確認無引用遺失、關鍵歷史傷病查詢等價、留存資料與壓縮副本對得起來。逐表回收空間，每次確認 WAL、磁碟餘量以及網站和 Railway 心跳。若鎖無法取得、核對有差異或磁碟空間不足，停止進入下一步。`VACUUM FULL` 會短暫鎖表並需要暫存磁碟空間。[PostgreSQL VACUUM](https://www.postgresql.org/docs/current/sql-vacuum.html)
5. 完成後確認實際 NBA 與組織容量。日後接近額度時可重跑相同的唯讀預估，並按當時截止日處理冷資料。舊日的已取代快照需從歸檔稽核或還原，日常頁面仍可顯示各日最新快照。若需回填古早傷病的球員對應，先在隔離環境還原，驗證後才更新壓縮副本。

資料庫容量與 Egress 的額度分別計算。已用流量等下個帳期重置。Fair Use 判斷容量還會看帳期內的每日平均，資料檔整理完成與組織限制解除可能不同步。[Fair Use 資料庫容量規則](https://supabase.com/docs/guides/platform/database-size#fair-use-database-size-restriction)
