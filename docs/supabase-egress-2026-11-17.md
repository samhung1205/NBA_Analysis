# Supabase 免費額度再次超標（2026-11-17）

Supabase Usage 顯示，本期 11/15–12/15 出站流量為 7.624 GB / 5 GB，NBA 專案占 7.619 GB。組織已因 Egress Exceeded 套用 402。NBA Database Size 約 765 MB。直接 PostgreSQL 仍可讀，Railway 排程仍在運作。官方說明指出，已累積流量留在當期帳單，額度限制在下個帳期重置後解除，可能稍有延遲。[Egress 計量](https://supabase.com/docs/guides/platform/manage-your-usage/egress) · [組織 Fair Use 限制](https://supabase.com/docs/guides/platform/billing-faq#fair-use-policy)

## 反覆下載的原因與修正

- Railway 正式版 `6e6d964` 近兩天有 177 次歷史快取 miss，沒有 hit。原先用整數鍵排序後計算 checksum，JSON 回讀的鍵則是字串，像 2 和 10 的排序會對調。上次隔離測試沒覆蓋跨位數鍵，正式資料即使未變也反覆下載。
- 賽果和 box score 快取按 UTC 週儲存，傷病快取按 UTC 日儲存。只下載指紋改變的區段，回傳資料仍受原本 as-of 和傷病視窗限制。每批指紋與下載共用 read-only repeatable-read snapshot。快取放在既有模型 volume，預測子行程退出後仍可重用。每週重訓重用 box score 快取，完整歷史傷病仍以 cutoff 唯讀取得。
- 決策和注碼的盤口、預測、定價與 paper ledger 查詢，在同一個 SQL snapshot 比對完整結果指紋。相同時只回傳指紋，修正、結算或刪除時回傳新結果。決策中心只取台彩會用到的注碼來源參照。原有的 as-of、最新關盤、定價及風控規則仍由原本邏輯處理。

正式資料唯讀驗證在同一 as-of 首次讀取 6,810 場、145,565 筆球員資料、185 份近期傷病報告，建立 180 週及 6 天快取。第二次 186 個區段全部命中，明細下載數 0。單次量測耗時約 97 秒首次載入、4.1 秒再次載入。這是本機執行新版程式連正式 DB 的量測，快取放在本機私有暫存，完成後移除。正式部署後需以 Railway `[input-cache]` 紀錄與 Supabase Usage 每日曲線檢查月額度是否足夠。

同一正式快照上，決策中心當天輸入與 paper evidence 的唯讀測試，首次回傳 896 列，第二次回傳 13 列，應用層結果相同。列數差異為單次樣本，與整月流量分別記錄。

離線 712 項通過。隔離 Postgres 共 26 個不同案例通過，涵蓋跨位數 ID、完賽週更新、傷病更正、快取毀損、as-of、關盤、注碼與決策一致性，以及查詢結果修改與刪除。正式部署尚待授權。

## 資料庫容量

以正式唯讀查詢量測，大宗為傷病明細約 233 MB、決策機會約 215 MB、注碼快照約 154 MB、定價快照約 51 MB（含索引，以十進位 MB 近似）。一般 VACUUM 無法移除仍有效的歷史列。10/01 前有 900,066 筆傷病明細，其中部分用於歷史重訓。11/10 前有 136,315 筆目前未直接連在決策機會上的 sizing snapshots，這批仍是歷史證據。兩批資料可作為歸檔評估範圍，實際節省須透過隔離還原和重建量測，並預留持續成長空間。

具體容量路徑是保留一份可還原的全庫備份，將 NBA 的 Postgres 移至已有容量的獨立環境，讓網頁與排程驗證後切換。同一 schema 可保留使用者、下注與稽核外鍵，避免拆散歷史與線上證據。替代路徑是在目前實例歸檔歷史傷病與舊注碼，讓重訓／稽核能讀取歸檔。這需要把完整的資料讀取、校驗、回滾與空間回收都先在隔離環境驗證，才能評估正式移除。歸檔和搬遷尚未執行。
